# vitest stubs CSS imports to the empty string

Do NOT write a test that reads a `.css` file through the bundler, including Vite's `?raw` suffix; this project's vitest setup stubs CSS imports to `""`, so `import css from "./tokens.css?raw"` yields an empty string and every assertion against it passes vacuously (a probe test confirmed `type=string len=0`). `node:fs` is not the workaround either: the frontend tsconfig has no `@types/node`, so importing it breaks `tsc` (this is what shipped broken in `3275344`). Put structural assertions about CSS in a plain Node script that already gates the suite, `scripts/check-tokens.mjs`, instead.

**This has now bitten twice.** The second time added a case: for a **`.module.css`** file, `?raw` does not yield `""` but the **CSS-Modules proxy object**, so `css.replace(...)` throws `TypeError: css.replace is not a function` and `String(css)` throws `Cannot convert a Symbol value to a string`. Same conclusion, louder failure. Both attempts were made without reading this entry first; check here before writing any CSS assertion, and reach for `scripts/check-tokens.mjs` immediately rather than rediscovering the two dead ends.

**Third time, #101.** A plan to guard the Omnibox's height bound drafted the check as a `?raw` source-scan test and only reached `check-tokens.mjs` after an adversarial pass argued the mechanism had no precedent here. Right destination, entirely re-derived, entry still unread. **There is a one-command tell that skips all of this:** `grep -rn '\.css?raw' src/` returns nothing, and it always has. In a codebase that reads `.ts`, `.tsx`, `.json`, `.jsonl` and `.rs` through `?raw` constantly, a stylesheet never being read that way is not an oversight, it is this entry. Absence of precedent for a mechanism this repo would obviously have used is itself the warning.
**Fourth time, this ticket.** Both documented dead ends were walked in order, in one sitting: `node:fs` first (`tsc` failed on `Cannot find module 'node:fs'`, exactly as this entry says it does), then `?raw` (a probe printed nothing and the suite failed vacuously), then `check-tokens.mjs` as check 10. The entry was not read until afterwards. Four hits, four rediscoveries, so treat the grep tell above as mandatory rather than clever: run `grep -rn '\.css?raw' src/` before writing any assertion about a stylesheet.
**Fifth time, subagent lanes.** A test for the lane strip's surfaces reached for `import.meta.glob("./Chat.module.css", { query: "?raw" })`, a spelling this entry had not seen, and got the proxy object back exactly as the second hit describes. Moved to `check-tokens.mjs` as check 11, then check 12 in a later phase. The grep tell would have caught it: five hits, five rediscoveries, and the only thing that has ever worked is running the grep first.
**Sixth time, the PDF viewer.** A guard was needed for the `.textLayer` rules copied out of pdf.js, so the draft was a `src/panels/Editor/pdfTextLayerCss.test.ts` reading the sheet with `node:fs`. It ran green under vitest and `tsc --noEmit` then failed with `Cannot find module 'node:fs'`, which is the sentence in the second paragraph of this entry. Moved to `check-tokens.mjs` as check 11. Note what the grep tell cannot catch: this attempt never touched `?raw`, so `grep -rn '\.css?raw' src/` was silent and correct. **The wider rule is the one to carry: any structural assertion about a stylesheet belongs in `scripts/check-tokens.mjs`, whichever mechanism you were about to reach for.**
