# pdf.js inside Sway's webview

pdf.js is not a library you import and call. It is a library plus a worker script plus four directories of runtime data plus a stylesheet contract, and three of those four things are fetched by URL at runtime rather than bundled. Getting it running inside a Tauri webview is mostly a question of who serves what, and of noticing when it has quietly degraded instead of failing.

## How it works

- **One module names it, and only a dynamic import reaches that module.** `src/panels/Editor/pdfjsRuntime.ts` is the sole static reference to `pdfjs-dist`; `pdfDocument.ts` reaches it through `import("./pdfjsRuntime")`, latching `null` on failure so a later open retries. `src/test/lazyEditorBoundary.test.ts` fences both the package specifier and that module out of the entry's static graph. Result: three chunks, entry `+2,086` bytes over the whole feature's first phase, `PdfView` at 6.9 KB, `pdfjsRuntime` at 483 KB, plus the worker as a 1.27 MB asset. A session that never opens a PDF pays the entry cost only.
- **The worker and the data are served by a Vite plugin, not by `public/`.** `sway-pdfjs-data` in `vite.config.ts` serves `/pdfjs/` from `node_modules` in dev and emits the same files into the bundle at build: `pdf.worker.min.mjs`, and the `cmaps`, `standard_fonts`, `wasm` and `iccs` directories (about 4 MB). Without those four, a PDF using CJK encodings, an unembedded base-14 font or a JBIG2/JPEG2000 image simply will not open. They come out of `node_modules` because committing 4 MB of generated data to `public/` is not a thing to do. The plugin serves only paths it spells out and refuses `..`; a `.mjs` goes out as `text/javascript`, which a module worker requires.
- **The worker is Sway's, not pdf.js's implicit per-document one.** `sharedWorker()` in `pdfDocument.ts:112` constructs one `PDFWorker` per session and passes it to every `getDocument`, which is also what keeps `task.destroy()` from taking the worker down with the document.
- **A failed worker is silent, so the check is the absence of a line.** pdf.js answers a worker script that will not load by parsing on the main thread instead, with no error. `worker.port instanceof Worker` is the tell: a real worker, or a same-thread loopback port. `pdfDocument.ts:123` warns **in every build** when it is the loopback one, so silence means the worker is real. `import.meta.env.DEV` was the wrong gate here: a DEV-only info log cannot answer a question about the release build.
- **The transport is `asset://`, over XHR, whole.** `getNetworkStream` treats only `http(s)` as fetchable and picks `PDFNetworkStream` for anything else (`pdf.mjs:14368`), which sets `isHttp = false`, sends no `Range` header and accepts only a 200. So `convertFileSrc(path)` loads the file in one piece before the first page renders. That is the honest ceiling and it is fine for the PDFs a coding tool meets; no `fs_read_bytes` fallback was needed.
- **The text layer's CSS is a copied contract, pinned by a build check.** `TextLayer` writes `--font-height`, `--scale-x` and `--rotate` per span and `--min-font-size` on the container, and reads `--total-scale-factor`, `--scale-round-x` and `--scale-round-y` back through `setLayerDimensions`, which is what actually sizes the layer's box (`width: round(down, var(--total-scale-factor) * <page>px, var(--scale-round-x))`). pdf.js only ever reads `--total-scale-factor`; nothing in the library sets it, so `PdfView` writes the CSS-px-per-point scale inline on each page div. `pdf_viewer.css` is not imported (colour literals, `color-scheme: only light`, two thousand lines of viewer chrome), so `PdfView.module.css` carries a minimal copy pinned to pdf.js 6.3.289 by check 11 in `scripts/check-tokens.mjs`.
- **The floor is Safari 18.2.** pdf.js 6.3 calls `Promise.try` and `Uint8Array.prototype.toHex` without feature-detecting either, and both fail at module evaluation. That is what makes an import failure the whole capability probe: `PdfRuntimeError` already covers the old-WebKit case, and the tab says so in one sentence rather than going blank.

## Why it's this way

The four runtime data directories and the worker are the parts nobody plans for, because the library's own README implies they are optional. They are not: they are the difference between a viewer that works and one that fails on a subset of real files, silently in the worker's case. Serving them from a plugin rather than `public/` keeps generated bytes out of git and keeps dev and release emitting the same paths, which is the property the `?url` bug destroyed ([[lesson_a_url_import_is_transformed_in_dev_and_copied_at_build]]).

Copying the stylesheet rather than importing it was a token-layer decision ([[adr_ui_config_system]]): `pdf_viewer.css` would have put colour literals and a forced light colour scheme into a themed app. The cost is that the copy can drift, and nothing in the normal toolchain can see that: every property in it is written or read by pdf.js at runtime, so `check-tokens`' `var()` resolution cannot tell a live declaration from a dead one and jsdom has no layout to measure. Check 11 exists because there was no other place to put that guard.
