# Feature list: the sidebar's Features mode

**Location:** `src/panels/LeftSidebar/` (key files: `FeatureList.tsx`, `FeatureItem.tsx`, the mode in `LeftSidebar.tsx`) and `src/components/Dialogs/` (`NewFeatureDialog.tsx`, `RepoChecklist.tsx`, `ConfirmDeleteFeature.tsx`, `FeatureWorktreeSweepDialog.tsx`, `WorktreeRemoveDialog.tsx`)

The read and write UI of a Feature ([[concept_feature_workspace]]) in the left sidebar: a persisted `Spaces | Features` mode, one row per Feature with a chip per member, a dialog that creates a Feature or adds repositories to one, and a context menu for Rename, Add repository and Delete. It renders what [[component_feature_store]] records, and since #154 a row click selects the Feature: the selection itself, its key and its consumers are [[component_feature_selection]].

## Responsibilities

- The mode. `LeftSidebar.tsx:251` `LS_MODE = "tori.sidebar-mode.v1"`, a `SegmentedControl` above `.treeSearch`, and the `toggle-sidebar-mode` command dispatched as `TOGGLE_SIDEBAR_MODE` (`utils/events.ts`). In Features mode the space rail and the Spaces tree are unmounted, the search box stays and filters Features by name or member display name, and `props.selected` is never touched.
- The list. `FeatureList.tsx:28` is mounted only in Features mode, so it owns its fetch and its listeners: `list_features` on mount with a latest-request-wins guard, `features://changed` applied as is (`apply`, `:51`, replace by id or append, no refetch), `config://changed` refetching. Subscriptions land after the first `await load()`, so a step in that window arrives with the settle's `config://changed`.
- The row. `FeatureItem.tsx:27`: name on one line with the branch in `title`, chips sorted by `order` and capped at `CHIP_CAP = 6` plus `+N`, each tinted by the Space whose project path matches `repoPath` (`spaceHue`/`spaceHueRgb`, neutral outside every Space), a `role="img"` badge for `worktree-missing` / `repo-missing` / `failed`, a Retry button per failed member, and the whole row rendered as `ContextMenu as="li"` so the menu needs no wrapper.
- The dialog. `NewFeatureDialog.tsx:28` with no `feature` creates; with one it adds repositories (no name field, slug fixed from `feature.branch`, members excluded, `add_member` once per pick in order). It runs `probe_feature_branch` per checked repo, keyed on `(repoPath, slug)` and dropped when either moved on (name edits debounced 250ms, a check probes at once). A hit shows "feat/<slug> already exists" with Adopt (an acknowledgement only: the backend reuses the branch and a secondary worktree on its own) and a button that unchecks the repo ("Rename this Feature", which refocuses the name, or "Leave out" in add mode). Done needs a non-empty slug, one repo, no slug already used by another Feature, and no row pending or collided; the dialog stays open with the message on rejection. This tightens #151, where Done needed only a name and a repo.
- The checklist. `RepoChecklist.tsx:19`: one `CheckboxGroup` per Space, root Spaces first then pinned, reporting paths in rail order whatever the click order; `exclude` drops repos and any Space left empty; the `collision` slot is a component under the row so a probe landing does not remount the checkboxes.
- Feedback and the menu. `settled` in `FeatureList` closes the dialog, applies the record, and toasts every member left `failed` with one Retry action; the menu rows are Rename (`PromptModal` then `rename_feature`, patched locally), Add repository (the dialog in add mode) and Delete (a `ConfirmDialog` listing each member with its state, then `delete_feature`).
- Selection (#154). `FeatureList` takes `activeId`, `onSelect(feature)` and `onDeleted(feature)`; `FeatureItem` selects on a row-level `li` click (`aria-current` on the active row, Retry stops propagation so it does not also select) and there is no keyboard path, the unit rows' pattern. `remove` calls `purgeWorkspace(featureKey(id))` after `delete_feature` and then `onDeleted`; the sidebar hands the shell `featureSelection(f, storedActiveRoot)` through one `selectFeature` used by both the row and the Spaces chip.
- The change count (#157). `FeatureList.tsx:140 changedIn(feature)` sums `gitStateFor(m.worktreePath).files.length` over the Feature's **own** members and hands it down as `FeatureItem`'s `changed` prop, rendered as `N changed` beside the name so the row height never moves. Asked per member rather than totalling the git slot map, and not gated on `activeId`: the editor only ever enters the open Feature's roots, so every other row sums to zero and stays silent on its own, and no row can be handed a number the Feature beside it measured ([[lesson_attribute_a_number_by_what_measured_it]]). Zero renders nothing, so a clean open Feature is silent too. It counts every file a member holds, staged and conflicted included, because a number that empties when you stage is a number you stop reading. `FeatureItem` reads no store, which is what keeps `FeatureItem.stories.tsx` rendering the row from args alone. That the count is keyed by root makes worktree identity load-bearing: two Features over one repo do not collide only because the worktree path carries the Feature's slug, which is why the `FeatureList.test.tsx` fixtures stopped using `worktreePath: null`.
- The other home. The sidebar keeps its own `features` signal (same two feeds) so a member unit row in Spaces wears an `in <Feature>` chip (`LeftSidebar.tsx:2152 featuresAt`) that opens the Feature with that folder active, and `unitSelected` refuses a feature Selection so no unit reads active while a Feature is selected.
- **The member list (#159).** `FeatureItem`'s disclosure opens one row per member in `order`, **uncapped**: `CHIP_CAP` plus `+N` means a seventh member has no chip, and rename, reorder, repair and remove cannot be unreachable for a member the Feature still holds. Each row is a `ContextMenu as="li"` carrying Rename, Move up, Move down (disabled at the ends) and Remove repository, plus the member's repair button when `memberState().action` names one. The disclosure state is **controlled-optional**: `expanded` + `onExpand`, held by `FeatureList` keyed by feature id, because applying a record replaces the object the `<For>` keys on and a row's own signal would shut the list on the very actions it exists to offer. Uncontrolled when `onExpand` is absent, which is what the stories and `FeatureItem.test.tsx` use.
- **Drag-reorder, shared (#159).** `utils/dragReorder.ts` `createDragReorder({ keys, onCommit })` is the one gesture, used by the expanded rows and by the Toolbar chip row. The carried key lives in a signal rather than in `dataTransfer` (the drop only ever lands in the same list), `rowProps(key)` is deliberately static with the reactive part read in a `classList`, and `fromDrag()` implements `OverflowTabBar`'s press-that-never-becomes-a-click rule so carrying a Toolbar chip does not also switch the active root. The drop indicator is the **whole row**, not a top edge: `moveKey` lands the carried member where the target sits, which reads as "above" going up and "below" going down.
- **Repair, off `memberState().action` (#159).** `onRepair(member, action)` replaces `onRetry`; the row decides nothing. Recreate and Retry go to `retry_member`, Locate runs `pick_folder` then `relocate_member` and a cancelled picker leaves the record exactly as it was. The button's label comes from `REPAIR_LABEL` in `utils/features.ts`, the same table [[component_project_file_tree]] and [[component_changes_panel]] draw from, so the label and the command behind it cannot disagree.
- **Remove repository (#159).** The record detaches first, as the ticket specifies, and only then is the worktree offered, which is why `WorktreeRemoveDialog` grew an optional `keepLabel` reading "Keep worktree" here and "Cancel" everywhere else: cancelling after the record is gone would read as an undo the dialog cannot perform. A **usable** member only: `reconcile_member` never clears `worktree_path`, so a broken one still carries a folder git cannot reach through its repo. Removing the open Feature's member re-selects it from the reloaded record through `props.onSelect`, so `featureSelection` drops the departed root from `roots` and moves `activeRoot` off it when it was the active one, before anything touches the folder. Guarded on `activeId`, so a removal elsewhere never switches the workspace.
- **Delete, in two questions (#159).** `ConfirmDeleteFeature` lists every member with what `worktree_status` says about its worktree (a member with nothing usable shows its state instead), then `FeatureWorktreeSweepDialog` offers each worktree Keep or Remove with a "delete `feat/<slug>`" checkbox. That checkbox **follows the evidence on its own row**: `at(m).branch ?? clean(m)`, so untouched means whatever git said and a status landing late still moves the default while an explicit tick outranks it. The single-worktree dialog defaults local-delete on, which is calibrated for one tree whose warning is in the same dialog; over N rows the warning has to reach the row. Each row also says how many terminal tabs removal stops (`countRunning`, a prop, since the sidebar owns the live-tab list). The sweep opens **only after** `delete_feature` succeeds and after `purgeWorkspace`, and every Remove row goes through `utils/memberWorktree.ts` `removeMemberWorktree` under `Promise.allSettled`, so one repo refusing keeps its own worktree and nobody else's; failed rows stay on screen with git's reason.
- **The refusal is drawn, not hovered.** Remove repository on the last member is `refusing` (aria-disabled, still arrow-reachable, does nothing) with `LAST_MEMBER` under the label through `MenuItem.note` and `aria-describedby`, because `src/test/interactiveTitle.test.ts` bars a native `title=` on a `role="menuitem"`.
- Does NOT rename branches (frozen at creation) or change the Spaces tree beyond unmounting it and the chip. It no longer avoids removing worktrees: Remove repository and the delete sweep both do, always through `removeMemberWorktree`.

## Two async gaps worth knowing about

Both were found in self-review and both needed a test that can hold **two** backend answers open, not one ([[lesson_a_test_that_passes_against_the_broken_code]]).

- The delete confirm closes before `delete_feature` is awaited and the sweep opens after it, so a `worktree_status` resolving in between has no dialog to land on. The folded answers are kept in a plain `statuses` map that both dialogs are rehydrated from, or that row reaches the sweep permanently reading "checking...".
- "Keep all" stays live while the removals run, so a row failing after the user dismissed the sweep called `setSweepReq` on a captured request and brought it back. Guarded on `sweepReq()` still being non-null.
